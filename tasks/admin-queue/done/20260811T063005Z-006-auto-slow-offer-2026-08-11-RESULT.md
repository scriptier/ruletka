## What changed

Pulled real production evidence first (`./scripts/hub-match-speed.sh 720
2000`, read-only `journalctl -u roulette-bridge` grep against the live hub,
69 matches / 58 offers over 12h), then made one small, low-risk fix based on
what the evidence actually showed.

**Finding:** `match_to_offer_ms` for the web offerer (web is always the
preferred offerer per CONNECTIVITY_LOCK) is **trimodal**, not evenly spread:

| cluster | samples (ms) | share |
|---|---|---|
| healthy | 200–2369 (most &lt;1000) | ~34/58 |
| mid-stall | 8549–9415 (7 samples, 866ms band) | 7/58 |
| hard-stall | 25533–26176 (8 samples, 643ms band) | 8/58 |

Both stall clusters are too tight to be network jitter — they're a
deterministic recovery-timer tail firing. `armOfferKickWatch` (`ui/live.js`)
re-kicks a stuck first offer at fixed delays and, on its **last** wave,
tears down and rebuilds via `kickSoloWebRtc()`. That rebuild itself can take
several seconds under load (mid-stall cluster ≈ last wave + rebuild time).
When the rebuild also stalls, nothing was scheduled after it — the ladder
just stopped, so real recovery had to wait on some other/later mechanism,
landing in the ~25.5s hard-stall cluster.

**Fix:** extended the retry ladder's tail with two more spaced-out waves
(still ≥3s apart — hub's own offer debounce is ~3.5s — and still gated by
the existing `hasRealSdp()` / `hasLiveRemoteMedia()` no-op guards, so a
wave that fires after a real offer is already on the wire does nothing):

- normal: `[400, 1200, 2500]` → `[400, 1200, 2500, 6000, 9500]`
- `force_relay`: `[800, 2000, 4000]` → `[800, 2000, 4000, 8000, 12000]`

Does not touch hub `force_relay` policy, offer debounce, answerer behavior,
or add any new offer/answer code path — it's an additive extension of the
same self-healing ladder already in place.

Full evidence tables, root-cause writeup, and a follow-up checklist (why the
rebuild itself takes several seconds — likely non-trickle ICE gathering
before first emit; offer `payload_len` is consistently ~7500 bytes,
confirming candidates are already baked in) are in
`docs/CONNECTIVITY_SPEED_PLAN.md` under the new "2026-08-11 — match→offer
latency budget" section.
